# Phase 3.3 — Orientation (task T0)

Maps [the 3.3 spec](sharpclaw-3.3-implementation-spec.md) onto the repository as it stood after the
pre-3.3 foundations (#129). The human asked for the whole phase in one pull request without
pausing, so the conflicts below were resolved with the decisions listed rather than by stopping.

## 1. Foundations check

All prerequisites are merged: session-cookie auth with CSRF (`Auth/ClientAuthFilter.cs`,
`Auth/AuthEndpoints.cs`), tool exchanges in history (`includeTools`, `MessageKinds`), context info
on threads (`ThreadContextDto`), durable SSE events with replay and the global `/api/events`
stream (`Endpoints/EventStreamResult.cs`, `Services/EventPublisher.cs`), and the approvals queue
(`Endpoints/ApprovalEndpoints.cs`).

## 3. Answers to the T0 questions

- **Risk levels** (`Contracts/Constants.cs` `RiskLevels`): `low`, `medium`, `high`, `critical`.
  The highest, `critical`, needs the UI's second confirmation step.
- **Provider tool-call id:** `tool_calls.tool_call_id` stores it (unique with the correlation id),
  and tool messages carry the same `toolCallId`, so the UI can enrich tool cards from the trace.
- **Fake provider:** already scripts tool calls (`toolCalls` in rules, `role: "tool"` matching)
  and every error type. Approvals come from the agent's own policy (`allowedRiskLevel`), so the
  end-to-end stack needs an agent config that requires approval for a scripted tool; no provider
  change was needed.
- **CI workflows:** none exist (`.github/` holds only Copilot instructions). The UI and snapshot
  checks are run locally (`npm run check:api`, `dotnet test`); adding CI is left to the human.

## 4. Conflicts and decisions

| # | Spec vs code | Decision |
|---|---|---|
| 1 | §5.1's list row has no `context`, but the pre-3.3 list returned it. | The list follows the spec; context is on `GET /api/threads/{id}` (and `ThreadDto` from create/patch). One existing test moved to the detail endpoint. |
| 2 | §5.3 trace tool calls list `outcome`; the table column is `status`. | `outcome` is the `status` value. `toolCallId` is added so cards can be linked. `createdAt` (the user message's) is added to each turn. |
| 3 | §5.7 "every payload includes `threadId`": `ready` and `reset` on the global stream have no thread. | They carry `threadId: null` on the global stream. Other payloads gained a trailing `ThreadId` so existing positional call sites still compile. |
| 4 | §5.2 default `limit` (100) applies with no cursor; the CLI fetched all rows. | The CLI only looks for the reply to its latest turn, which is always in the latest page. |
| 5 | §7 needs plain integer schemas; web JSON defaults allowed numbers as strings, giving `["integer","string"]`. | Request JSON number handling is now strict (`JsonNumberHandling.Strict`). |
| 6 | §6 SPA fallback should not catch `/openapi`; the doc is authenticated. | `/openapi/v1.json` is behind the same client filter as `/api/*`; `/openapi/*` is `no-store`. |
| 7 | §11 Playwright "against the Compose stack". | The suite takes `E2E_BASE_URL`; `ui/e2e/stack.sh` starts an isolated gateway + agent (fake provider) on spare ports so it never disturbs a running Compose stack. |
| 8 | §8.3 `tool.requested` payload has no arguments (by design). | Live rows show the tool name and "running…" only. |
